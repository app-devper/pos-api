# 01. Auth and Access Control

## วัตถุประสงค์ทางธุรกิจ

ควบคุมการเข้าถึงข้อมูลและฟังก์ชันของระบบให้สอดคล้องกับบทบาทงานจริง ลดความเสี่ยงจากการเข้าถึงข้อมูลยา ข้อมูลผู้ป่วย และรายงานตามกฎหมายโดยไม่ได้รับอนุญาต

## ผู้มีส่วนเกี่ยวข้อง

- `SUPER`
- `ADMIN`
- `USER`
- ระบบจัดการผู้ใช้ภายนอก (UM API)

## ขอบเขตความรับผิดชอบ

- Backend ตรวจสอบ token, session, branch context, และ role authorization
- Frontend แสดงเมนูและหน้าใช้งานตามสิทธิ์ที่ผู้ใช้มี
- สิทธิ์เชิงธุรกิจต้องบังคับที่ Backend เสมอ แม้ Frontend จะซ่อนเมนูแล้วก็ตาม

## Business Rules

### 1. Authentication

- ผู้ใช้ต้อง login ผ่าน UM API ก่อนใช้งานระบบ POS
- เมื่อ login สำเร็จ ระบบต้องได้ token ที่ใช้กับ POS API ได้
- หาก token หมดอายุ ต้องบังคับ login ใหม่หรือ refresh session ตาม flow ของระบบ

### 2. Authorization

- `SUPER` เข้าถึงทุก feature ได้
- `ADMIN` เข้าถึง feature เชิงจัดการระบบและรายงานได้ตาม requirement
- `USER` เข้าถึงเฉพาะงานขาย งานข้อมูลพื้นฐาน และงานที่ไม่ใช่งานบริหารเชิงนโยบาย
- รายงาน ข.ย., การตั้งค่าระบบ, และการจัดการผู้ใช้ เป็น restricted feature

### 3. Branch Context

- ข้อมูลที่มีผลด้านธุรกิจต้องผูกกับสาขาเสมอ
- ถ้าผู้ใช้ไม่มี branch context ที่ถูกต้อง ระบบต้องไม่อนุญาตให้ทำรายการที่กระทบข้อมูลหลัก
- รายงานและข้อมูลสรุปต้องแสดงเฉพาะข้อมูลของสาขาที่ผู้ใช้มีสิทธิ์

### 4. Session Integrity

- การเรียก API ที่ต้องใช้ข้อมูลสำคัญต้องตรวจว่า session ยัง valid
- ถ้า session invalid ระหว่างใช้งาน ต้องป้องกันไม่ให้บันทึกรายการครึ่งทาง

## Validation Rules

- token ต้องมีรูปแบบถูกต้องและตรวจสอบได้
- role ต้องตรงกับ action ที่ร้องขอ
- branch ต้องมีและใช้ได้กับทรัพยากรที่ร้องขอ
- คำสั่งแก้ไขข้อมูลสำคัญต้องไม่ bypass authorization

## กรณีพิเศษ

- ผู้ใช้ role ต่ำเรียก endpoint โดยตรง ต้องโดนปฏิเสธจาก Backend
- Frontend อาจแสดงผลผิดชั่วคราวจาก state เก่าได้ แต่ Backend ต้องเป็นแหล่งตัดสินสุดท้าย
- ถ้าระบบ UM API ไม่พร้อมใช้งาน ระบบ POS ต้องไม่สร้าง local trust โดยไม่มีการพิสูจน์ตัวตน

## Audit Expectations

- ควรตรวจสอบได้ว่าใครทำรายการอะไร เมื่อใด ที่สาขาใด
- รายการที่เกี่ยวกับสิทธิ์สูงควรมี trace ย้อนหลังได้
