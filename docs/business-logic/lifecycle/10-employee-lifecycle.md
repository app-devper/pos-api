# 10. Employee Lifecycle

## วัตถุประสงค์

กำหนดสถานะของพนักงานในระบบเพื่อให้การใช้งานข้อมูลบุคลากร การผูกกับสาขา และการอ้างอิงในเอกสารหรือ workflow ต่าง ๆ มีความชัดเจน

## สถานะหลัก

- `DRAFT` — ข้อมูลพนักงานกำลังถูกสร้างหรือแก้ไข
- `ACTIVE` — พนักงานพร้อมใช้งานใน workflow ปกติ
- `INACTIVE` — พนักงานไม่พร้อมใช้งานใน flow ปัจจุบัน เช่น พักงานหรือเลิกใช้งานชั่วคราว
- `ARCHIVED` — เก็บข้อมูลไว้เพื่ออ้างอิงย้อนหลัง

## Transition หลัก

### 1. `DRAFT -> ACTIVE`

#### Trigger

- ผู้ใช้บันทึกข้อมูลพนักงานครบและเปิดใช้งาน

#### Preconditions

- มีข้อมูลระบุตัวตนและความสัมพันธ์กับสาขาที่ถูกต้อง
- หากผูกกับ user account หรือ role ต้องพร้อมใช้งาน

#### Backend Effects

- พนักงานพร้อมถูกใช้อ้างอิงใน flow ที่เกี่ยวข้อง
- ข้อมูลพนักงานพร้อมใช้ในหน้าจัดการบุคลากรและเอกสารที่ต้องแสดงชื่อบุคลากร

#### Frontend Behavior

- แสดงใน employee list และ selectors ที่เกี่ยวข้อง

### 2. `ACTIVE -> INACTIVE`

#### Trigger

- ปิดใช้งานพนักงาน

#### Effects

- ไม่ควรถูกเลือกใน workflow ใหม่ที่ต้องใช้พนักงานนี้
- ข้อมูลเดิมในประวัติหรือเอกสารยังต้องอ้างอิงได้

#### Frontend Behavior

- แสดงสถานะ inactive
- ป้องกันการเลือกใช้งานใน flow ใหม่

### 3. `INACTIVE -> ACTIVE`

#### Trigger

- เปิดใช้งานอีกครั้ง

### 4. `ACTIVE/INACTIVE -> ARCHIVED`

#### Trigger

- เก็บข้อมูลไว้เชิงประวัติระยะยาว

## ข้อควรระวัง

- ไม่ควร hard delete พนักงานที่มีข้อมูลเกี่ยวข้องในประวัติธุรกิจ
- การย้ายสังกัดสาขาหรือเปลี่ยนบทบาทต้องไม่ทำให้ข้อมูลย้อนหลังสับสน
