# 09. Branch Lifecycle

## วัตถุประสงค์

กำหนดวงจรชีวิตของสาขาในระบบเพื่อให้การผูกข้อมูลธุรกิจ การมองเห็นข้อมูล และการออกรายงานในระดับสาขามีความสอดคล้องกัน

## สถานะหลัก

- `DRAFT` — ข้อมูลสาขากำลังถูกสร้างหรือแก้ไข ยังไม่พร้อมใช้งาน
- `ACTIVE` — สาขาพร้อมใช้งานใน workflow ธุรกิจ
- `INACTIVE` — สาขาไม่เปิดใช้งานสำหรับการทำรายการใหม่
- `ARCHIVED` — เก็บข้อมูลสาขาไว้เพื่ออ้างอิงย้อนหลังโดยไม่ใช้ในงานปัจจุบัน

## Transition หลัก

### 1. `DRAFT -> ACTIVE`

#### Trigger

- ผู้ใช้บันทึกข้อมูลสาขาครบและเปิดใช้งาน

#### Preconditions

- ข้อมูลสาขาพื้นฐานครบ เช่น ชื่อ รหัส หรือข้อมูลที่ระบบต้องใช้
- ระบบพร้อมให้ผูกผู้ใช้ พนักงาน และข้อมูลธุรกิจกับสาขานี้

#### Backend Effects

- สาขาพร้อมถูกใช้เป็น branch context ของข้อมูลธุรกิจ
- setting, reports, orders, receives และ master data ที่ผูกสาขาสามารถอ้างอิงสาขานี้ได้

#### Frontend Behavior

- สาขาปรากฏใน selector หรือหน้าจัดการสาขา
- ผู้ใช้ที่มีสิทธิ์สามารถเลือกสาขานี้ใน workflow ที่เกี่ยวข้องได้

### 2. `ACTIVE -> INACTIVE`

#### Trigger

- ปิดใช้งานสาขา

#### Effects

- ไม่ควรมีรายการธุรกิจใหม่ผูกกับสาขานี้ใน flow ปกติ
- ข้อมูลย้อนหลังยังต้องอ้างอิงสาขาได้
- ผู้ใช้ที่ผูกกับสาขานี้อาจต้องถูกจำกัดการทำงานหรือย้ายสังกัดตามนโยบาย

#### Frontend Behavior

- แสดงสถานะ inactive ชัดเจน
- ซ่อนจาก selector ปกติ หรือแสดงแบบ disabled

### 3. `INACTIVE -> ACTIVE`

#### Trigger

- เปิดใช้งานสาขาอีกครั้ง

### 4. `ACTIVE/INACTIVE -> ARCHIVED`

#### Trigger

- เลิกใช้งานถาวรแต่ยังต้องเก็บข้อมูลประวัติ

## ข้อควรระวัง

- ห้าม hard delete สาขาที่มีข้อมูล order, receive, report หรือ setting แล้ว
- branch context เป็นแกนสำคัญของ authorization และ data isolation จึงต้องตีความสถานะอย่างเคร่งครัด
