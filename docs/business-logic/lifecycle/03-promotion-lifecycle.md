# 03. Promotion Lifecycle

## วัตถุประสงค์

กำหนดวงจรชีวิตของโปรโมชันเพื่อให้การสร้าง ใช้งาน เปิด/ปิด และหมดอายุสอดคล้องกับนโยบายการขาย

## สถานะหลัก

- `DRAFT` หรือข้อมูลที่กำลังแก้ไขบนหน้าเว็บ
- `ACTIVE` — พร้อมใช้งานกับการขาย
- `INACTIVE` — ถูกปิดการใช้งานชั่วคราวหรือถาวร
- `EXPIRED` — พ้นช่วงเวลาที่กำหนดและไม่ควรถูกใช้อีก

## Transition หลัก

### 1. `DRAFT -> ACTIVE`

#### Trigger

- ผู้ใช้บันทึกโปรโมชันที่ valid และเปิดใช้งาน

#### Preconditions

- code ไม่ซ้ำ
- ช่วงวันที่ถูกต้อง
- value และเงื่อนไขต่าง ๆ ผ่าน validation

#### Backend Effects

- บันทึก promotion record ในสถานะใช้งาน
- ทำให้ POS สามารถนำ promotion นี้ไปตรวจสอบได้

#### Frontend Behavior

- แสดงสถานะ active ชัดเจนใน list
- เปิดให้เลือกใช้ใน workflow ที่เกี่ยวข้อง

### 2. `ACTIVE -> INACTIVE`

#### Trigger

- ผู้ใช้ปิดใช้งานด้วยตนเอง

#### Effects

- โปรโมชันต้องไม่ถูก apply กับ order ใหม่
- ประวัติ order เดิมที่เคยใช้โปรโมชันนี้ยังคงข้อมูลเดิมไว้

#### Frontend Behavior

- แสดง badge inactive
- ซ่อนหรือปิด action ที่สื่อว่ายังใช้งานได้อยู่

### 3. `ACTIVE -> EXPIRED`

#### Trigger

- วันเวลาปัจจุบันเกิน `endDate`

#### Effects

- โปรโมชันหมดสิทธิ์ใช้งานอัตโนมัติในเชิงธุรกิจ
- POS ต้อง reject การนำโปรโมชันนี้ไปใช้กับ order ใหม่

#### Frontend Behavior

- แสดงสถานะหมดอายุอย่างชัดเจน
- แจ้งเหตุผลเมื่อผู้ใช้พยายามใช้งาน

### 4. `INACTIVE -> ACTIVE`

#### Trigger

- ผู้ใช้เปิดใช้งานใหม่

#### Preconditions

- โปรโมชันยังไม่หมดอายุ
- ข้อมูลหลักยัง valid

## ข้อควรระวัง

- ห้ามโปรโมชันถูกใช้หลังหมดอายุเพียงเพราะหน้าเว็บ cache สถานะเก่า
- การเปลี่ยนสถานะต้องไม่แก้ไขผลลัพธ์ของ order ที่บันทึกไปแล้ว
