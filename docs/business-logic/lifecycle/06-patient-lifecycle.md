# 06. Patient Lifecycle

## วัตถุประสงค์

อธิบายสถานะและวงจรชีวิตของข้อมูลผู้ป่วย เพื่อให้การใช้งานด้านความปลอดภัยทางยา การติดตามประวัติ และการปกป้องข้อมูลสุขภาพทำงานอย่างถูกต้อง

## สถานะหลัก

- `DRAFT` — ข้อมูลกำลังถูกสร้างหรือแก้ไข ยังไม่สมบูรณ์
- `ACTIVE` — ผู้ป่วยพร้อมใช้งานในระบบ เช่น เชื่อมกับ POS และดูประวัติการจ่ายยาได้
- `INACTIVE` — ไม่ใช้งานชั่วคราวหรือไม่ควรถูกเลือกในการทำรายการใหม่
- `ARCHIVED` — เก็บไว้เพื่ออ้างอิงย้อนหลังโดยไม่ใช้ในงานปกติ

## Transition หลัก

### 1. `DRAFT -> ACTIVE`

#### Trigger

- ผู้ใช้บันทึกข้อมูลผู้ป่วยครบขั้นต่ำตามนโยบายระบบ

#### Preconditions

- มีข้อมูลระบุตัวตนที่เพียงพอ
- หากมีข้อมูลแพ้ยาและโรคประจำตัว ต้องถูกบันทึกในรูปแบบที่ระบบใช้งานได้
- feature ผู้ป่วยถูกเปิดใช้งาน

#### Backend Effects

- patient profile พร้อมใช้งานกับ POS, allergy check และประวัติที่ผูกกับผู้ป่วย

#### Frontend Behavior

- สามารถค้นหาและเลือกผู้ป่วยในหน้า patients และหน้า POS ได้
- แสดงข้อมูลสุขภาพสำคัญ เช่น allergy อย่างเด่นชัด

### 2. `ACTIVE -> INACTIVE`

#### Trigger

- ผู้ใช้ปิดการใช้งาน record หรือ record ไม่ควรถูกเลือกใช้งานใหม่

#### Effects

- ไม่ควรถูกเลือกใน flow ปกติ เว้นแต่มี filter เฉพาะ
- ประวัติการจ่ายยาเดิมยังต้องอ้างอิงได้

#### Frontend Behavior

- ซ่อนจาก quick selectors หรือแสดงเป็น disabled
- หน้า detail ยังเปิดอ่านย้อนหลังได้หากผู้ใช้มีสิทธิ์

### 3. `INACTIVE -> ACTIVE`

#### Trigger

- เปิดใช้งานใหม่หลังตรวจสอบข้อมูลแล้ว

### 4. `ACTIVE/INACTIVE -> ARCHIVED`

#### Trigger

- เก็บข้อมูลไว้เชิง audit และประวัติ โดยไม่ใช้งานใน workflow ปัจจุบัน

## ข้อควรระวัง

- ข้อมูลผู้ป่วยเป็นข้อมูลอ่อนไหว ต้องไม่ถูกลบจนทำให้ประวัติการรักษาหรือการจ่ายยาเสียความหมาย
- การปิดใช้งานผู้ป่วยต้องไม่ทำให้ order history ขาด reference
